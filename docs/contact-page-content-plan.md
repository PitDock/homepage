# 無料相談ページ（/contact）コンテンツ改善案

最終更新: 2026-09-21
対象: `app/contact/page.tsx` / `app/contact/layout.tsx` / `app/api/contact/route.ts`
目的: 「無料相談のハードルを下げ、問い合わせ数（CV数）を増やす」
本ドキュメントはコンテンツ設計フェーズの成果物であり、実装コードの変更は含まない。

---

## 0. サマリー（結論）

現状の `/contact` は **「予約フォームのみのページ」** であり、コンテンツが実質ゼロである。
Hero（H1＋3行のリード）の直後にいきなりフォームが始まり、

- 相談すると何が得られるのか
- 相談後に何が起きるのか（売り込まれないか）
- 何を書けばいいのか

が一切示されていない。一方でフォームは **必須4項目＋最大25回の操作を要する希望日時欄** を要求する。
「情報ゼロ × 要求は最大」という構造が、相談のハードルを上げている最大の要因である。

改善の方向性は次の3点。

1. **ページの役割を「予約フォーム」から「相談のハードルを下げるランディングページ」に変える**（セクション追加）
2. **必須項目を3つに絞り、自由記述の必須を廃止する**（「何を書けばいいか分からない」の解消）
3. **「売り込まない」「契約を迫らない」「準備不要」を明文化する**（心理的安全性の提供）

なお改善はフェーズ分割が可能で、**フェーズ1（コピー・セクション追加のみ）はAPI改修不要**、
**フェーズ2（フォーム項目変更）はAPI改修が必要**である（詳細は §7）。

## 1. 現状把握

### 1.1 `/contact` の現状構成

| 順 | セクション | 内容 |
|---|---|---|
| 1 | Nav | 共通 |
| 2 | Page Hero | パンくず／H1「無料相談のご予約」／リード3行（うち1行は「※本フォームからの営業は受け付けておりません。」） |
| 3 | フォーム | 会社名/部署・役職名（必須）・お名前（必須）・メールアドレス（必須）・ご相談内容（必須）・ご希望日時（第1〜第5希望）・送信ボタン「予約を送信する →」 |
| 4 | 送信完了 | 「ご予約を受け付けました」＋送信内容の表示＋「トップページに戻る」 |
| 5 | Footer | 共通 |

**現状のHeroコピー（原文）**

> H1: 無料相談のご予約
> リード: DX推進・AI活用・システム開発など、どんな段階のご相談も歓迎です。
> まずはお気軽にご予約ください。初回相談は無料です。
> ※本フォームからの営業は受け付けておりません。

**現状のフォーム仕様（`page.tsx` より）**

- 必須: `company`（会社名 / 部署・役職名）、`name`、`email`、`content`
- 任意（ただし画面上に「任意」表記なし）: `date1`〜`date5` の各 `Date` / `Start` / `End`
- 希望日時: 日付（最短は翌日）＋ 開始時・分 ＋ 終了時・分。時は 09〜21、分は 00/15/30/45
- バリデーション: 1枠に部分入力があると全項目必須／終了>開始／**30分以上の幅が必要**
- プライバシーポリシー同意チェックなし（`/partner` にはある）

**送信完了メッセージ（原文）**

> ご予約を受け付けました／無料相談のご予約ありがとうございます。翌営業日中にはご入力いただいたメールアドレス宛にご連絡させていただきます。

### 1.2 流入元ページのCTA文言

| 流入元 | 位置 | 文言 |
|---|---|---|
| `app/page.tsx` | Hero | まずは相談してみる（無料） |
| `app/page.tsx` | 課題セクション中間 | あなたの課題を無料で相談する → |
| `app/page.tsx` | Footer CTA | 無料相談を予約する（見出し「『何をするか決まっていない』で大丈夫です。」） |
| `app/service/dx-ax/page.tsx` | Hero / Footer CTA | 無料相談を予約する →（見出し「まずは、お気軽にご相談ください。」） |
| `app/service/system-dev/page.tsx` | Hero / Footer CTA | 無料相談を予約する →（見出し「開発のご相談、まずはお気軽に。」） |
| `app/service/tech-advisor/page.tsx` | Hero | まずは無料で相談する → |
| `app/service/tech-advisor/page.tsx` | Footer CTA | 無料相談を予約する →（見出し「まずは無料で相談する」） |
| Nav（全ページ） | 常時 | 無料相談する |

**重要な発見: 流入元と着地ページの温度差**

流入元は一貫して「**何も決まっていなくて大丈夫**」「**気軽に**」と約束している
（特にトップのFooter CTA「『何をするか決まっていない』で大丈夫です。」）。
ところが着地した `/contact` は、**「ご相談内容」を必須の自由記述で要求する**。
ユーザー体験としては「決まってなくていいと言われたのに、書けと言われた」という**約束の裏切り**になっており、
ここが離脱の主要因である可能性が高い。

## 2. 「相談しやすさ」を阻害している要因

### A. 心理的ハードル

| # | 要因 | 詳細 |
|---|---|---|
| A-1 | 「ご予約」という言葉が重い | 「予約」は日程を確定する行為を連想させる。「まだ検討段階だから予約はまだ早い」と感じさせる。CTA側は「相談してみる」なのにページは「ご予約」で言葉が揺れている。 |
| A-2 | 売り込まれる不安が放置されている | 「無料相談＝営業をかけられる場」というBtoBの一般通念に対し、否定材料が一切ない。 |
| A-3 | 相手が見えない | 誰が対応するのか、どんな人なのかが不明。小規模企業への発注判断では「誰が担当するか」が特に重要（コンテンツ仕様の代表紹介セクションの方針と同じ論理）。 |
| A-4 | 「営業お断り」がファーストビューにある | `※本フォームからの営業は受け付けておりません。` がH1直下に配置されている。書き手の防御姿勢が最初に目に入り、「選別されている」印象を与える。内容自体は必要だが位置が悪い。 |
| A-5 | 比較検討中・情報収集段階の人への許可がない | 「他社と比較中です」「すぐ発注はしません」でも良いという明示がなく、冷やかしと思われる恐怖がある。 |

### B. 入力項目の多さ・必須設定

| # | 要因 | 詳細 |
|---|---|---|
| B-1 | 「ご相談内容」が必須の自由記述 | 最大の障壁。悩みが言語化できていない人ほど離脱する。皮肉にも**PitDockが最も歓迎したい層**（要件が固まっていない層）を弾いている。 |
| B-2 | 1番目の必須項目が最も重い | 「会社名 / 部署・役職名」が先頭。しかも1フィールドに2情報をスラッシュ区切りで書かせる形式で、入力形式に迷う。役職のない人・個人事業主・創業前の人は答えづらい。 |
| B-3 | 希望日時の操作コストが極端に高い | 1枠あたり「日付＋開始時＋開始分＋終了時＋終了分」の5操作。5枠で最大25操作。モバイルではさらに負荷が高い。 |
| B-4 | 希望日時が任意だと分からない | 画面に「任意」表記がない。他項目に「必須」バッジがあるため任意と推測はできるが、5枠も並ぶ見た目が「全部埋めないといけない」圧力を生む。 |
| B-5 | 「30分以上の幅」ルールが事前に説明されない | 送信時に初めてエラーで知る。エラー体験は離脱率を押し上げる。 |
| B-6 | 選択可能時間帯（9:00〜21:45）の意図が不明 | 「夜間・土日も対応可」という強み（コンテンツ仕様 強み4）がフォームに実装されているのに、**言葉で説明されていない**ため価値として伝わっていない。→ §3.3 の補助テキストで明示する。 |

### C. 情報不足による不安

| # | 要因 | 詳細 |
|---|---|---|
| C-1 | 所要時間が書かれていない | サイト全体では「30分」を掲げているが、`/contact` には所要時間の記載がない。「何時間拘束されるのか」が分からない。 |
| C-2 | 実施形式が書かれていない | オンラインか対面か、使用ツール（Meet / Zoom / Teams）が不明。 |
| C-3 | 無料の範囲が書かれていない | 「初回相談は無料」とあるが、どこから有料になるかが不明で、後から請求される不安が残る。 |
| C-4 | 秘密保持への言及がない | 「社内の課題を外部に話してよいのか」という懸念に対する回答がない。NDAの可否も不明。 |
| C-5 | 準備物の有無が不明 | 「資料を用意しないといけないのでは」という負担感。 |
| C-6 | 個人情報の取り扱いに触れていない | プライバシーポリシー同意チェックがない（`/partner` にはある）。信頼面・運用面の両方で不足。 |
| C-7 | ページ内にFAQがない | サイト共通FAQはトップにあるが、相談そのものへの不安に答えるFAQは存在しない。 |

### D. 相談後の流れが見えない

| # | 要因 | 詳細 |
|---|---|---|
| D-1 | 送信後のプロセスが送信前に書かれていない | 「翌営業日中に連絡」は**送信完了画面にしか書かれていない**。送信を迷っている人にこそ必要な情報が、送信した人にしか見えない。 |
| D-2 | 面談の中身が分からない | 30分で何を話し、何を持ち帰れるのかが不明。 |
| D-3 | 面談後の流れが分からない | 提案・見積の有無、断り方、しつこく追いかけられないか、が不明。 |
| D-4 | 申込者への自動返信メールがない | `route.ts` はSlack Webhookに通知するのみ。申込者には**何も届かない**ため、「本当に送れたのか」が確認できず、返信までの1営業日が不安な空白になる。 |

### E. 導線・運用上の不整合

| # | 要因 | 詳細 |
|---|---|---|
| E-1 | 流入元の文脈が引き継がれない | どのページから来ても同じ画面。`/service/tech-advisor` から来た人も、トップから来た人も、同じ空欄の自由記述に向き合う。 |
| E-2 | `/shindan` LPとの運用が未整備 | コンテンツ仕様では `/shindan` のCTAは全て `/contact` に送り、「ご相談内容」に「業務棚卸し診断希望」と手入力させる想定。手入力依存は取りこぼしが発生する（※`app/shindan/` は現状空ディレクトリで未実装）。 |
| E-3 | 代替の連絡手段がない | 「フォームは面倒だからメールで」という層の受け皿がない。コンテンツ仕様のFooter CTAには副次CTA「メールで問い合わせる」が定義されているが、実装・記載がない。 |

## 3. 改善後のページ構成案

### 3.1 セクション順（推奨）

```
1. Page Hero（アイブロー＋H1＋リード＋安心バッジ＋フォームへのアンカーCTA）
2. こんなことでもご相談ください（相談テーマの例示）
3. 無料相談でお約束すること（やらないこと3つ）
4. 30分で、ここまで持ち帰れます（面談の中身）
5. お申し込みから相談までの流れ（4ステップ）
6. フォーム
7. よくあるご質問（このページ専用）
8. Footer
```

**設計意図**

- すでに相談意思が固まっている人は Hero のアンカーCTA（「相談フォームへ進む ↓」）で直接フォームへ飛べるため、セクション追加による迷いのコストは発生しない。
- 迷っている人には、フォームに到達するまでに「例示 → 約束 → 中身 → 流れ」を順に見せ、不安を1つずつ潰す。
- **担当者紹介の独立セクションは設けない**（決定事項D5）。代表が直接対応する事実は【4】の中に1行として溶かし込み、経歴等はトップページ・会社情報ページに委ねる。
- FAQはフォームの**後ろ**に置く。フォーム入力中に生じた疑問（「本当に無料？」「準備は？」）をその場で解消し、離脱を防ぐ。

**代替案（A/Bテスト候補）**: フォームを §3 の直後（＝上から4番目）に置き、説明系セクションを下に回す構成。
フォーム到達率は上がるが、不安が解消される前にフォームを見せることになる。
現状はすでに「フォーム先頭型」であり成果が出ていない前提のため、**まず推奨案を実装し、比較対象として現行を残す**ことを推奨。

### 3.2 各セクションのコピー

#### 【1】Page Hero

**アイブロー（H1上の小ラベル）**

```
無料相談（30分・オンライン・全国対応）
```

**H1（推奨案A）**

```
「まだ何も決まっていない」から、どうぞ。
```

**H1 代替案**

- 案B: `30分、話すだけ。それで十分です。`
- 案C: `無料相談のご予約`（現行維持。検索キーワード重視だが、ハードルは下がらない）

> 推奨は案A。`title` タグ側で「無料相談」キーワードを担保するため、H1は心理的ハードルを下げる役割に振り切ってよい。
> `/contact` は指名検索・内部回遊で到達するページであり、H1のキーワード最適化の優先度は低い。

**リード文**

```
DX推進、AI活用、システム開発、技術顧問。
どのテーマでも、「何から手をつけるべきか分からない」段階からのご相談を歓迎しています。

資料の準備は不要です。今いちばん困っていることを、そのまま話してください。
一緒に論点を整理するところからお手伝いします。
```

**安心バッジ（横並び4〜5点／アイコン付き）**

```
相談無料 ／ 所要30分 ／ オンライン（全国対応） ／ 平日夜間・土日祝も対応 ／ 資料の準備は不要
```

> 5点が多い場合は「資料の準備は不要」を省き4点とする。リード文で同じ内容に触れているため重複を許容できる。

**返信SLAの明示（バッジ下またはCTA直下・決定事項D6）**

```
お申し込みから翌営業日（土日祝を除く）までに、担当者よりご返信します。
```

**アンカーCTA**

```
[主要] 相談フォームへ進む ↓
[副次] 相談の流れを見る
```

**リスクリバーサル（CTA直下の小文字）**

```
その場で契約を迫ることはありません。お見積りのご提示も、ご希望があった場合のみです。
```

> `※本フォームからの営業は受け付けておりません。` は **Heroから削除し、フォーム送信ボタン付近の注記に移動する**（【6】参照）。

|---|---|

#### 【3】無料相談でお約束すること

**セクションタイトル**

```
無料相談で、PitDockがやらないこと。
```

**リード文**

```
「無料相談」と聞くと、営業を受けるのではないかと身構える方もいらっしゃいます。
PitDockの無料相談では、次の3つをお約束します。
```

**約束カード（3枚）**

| # | 見出し | 本文 |
|---|---|---|
| 1 | 売り込みはしません | サービスの説明から始めることはしません。最初の30分は、お客様の状況をお聞きすることに使います。PitDockが力になれない内容であれば、正直にそうお伝えします。 |
| 2 | その場で契約を迫りません | 面談中に見積書をお出しして判断を求めることはありません。ご提案やお見積りは、ご希望があった場合に後日お送りします。 |
| 3 | 資料の準備をお願いしません | 事前に整理された資料や要件定義書は不要です。口頭でのご説明だけで構いません。むしろ、整理されていない状態から一緒に考えるのがPitDockの仕事です。 |

**補足（任意・小文字）**

```
ご相談の内容は外部に開示いたしません。ご希望があれば秘密保持契約（NDA）の締結にも対応します。
```

> NDA対応は可能（決定事項D7）。この一文はそのまま掲載する。

#### 【4】30分で、ここまで持ち帰れます

**セクションタイトル**

```
30分の相談で、持ち帰っていただけるもの。
```

**リード文**

```
限られた時間ですが、「話して終わり」にはしません。
その場で以下までをお持ち帰りいただけるよう進行します。
```

**持ち帰れるもの（4カード）**

| # | 見出し | 本文 |
|---|---|---|
| 1 | 課題の輪郭 | 漠然としている悩みを、「何が本当の問題か」という形に整理してお返しします。 |
| 2 | 打ち手の選択肢 | 業務の見直し・ツール導入・AI活用・システム開発など、取りうる選択肢と、それぞれの向き不向きをお伝えします。 |
| 3 | 進める順番 | 「まず何から着手すべきか」の優先順位をお伝えします。PitDockに依頼せずに自社で進められる部分があれば、その方法もお伝えします。 |
| 4 | 費用と期間の目安 | ご希望があれば、想定される規模感・期間・費用のレンジをその場で口頭でお伝えします。 |

**当日の進行（オプション・タイムライン表示）**

```
0〜5分    ご挨拶と、本日お聞きしたいことの確認
5〜20分   現在の状況・お困りごとのヒアリング
20〜30分  論点の整理と、進め方のご提案
```

**締めの1行（担当者について・決定事項D5）**

```
営業担当ではなく、実際に手を動かすコンサルタント兼エンジニア（代表）が直接お話しします。
```

> 担当者紹介の独立セクションは設けず、この1行のみを置く（決定事項D5）。経歴に関心を持った人のために
> 「PitDockについて →」（`/company-info`）へのテキストリンクを併置する。
>
> ※進行の時間配分は運用実態に合わせて調整が必要。

#### 【5】お申し込みから相談までの流れ

**セクションタイトル**

```
お申し込みから相談までの流れ
```

**ステップ（4段）**

### 3.3 希望日時欄の改善案（決定事項E1 最終版: フリーテキスト）

現行は「日付 ＋ 開始時 ＋ 開始分 ＋ 終了時 ＋ 終了分」を最大5枠。操作数が最大25回で、フォーム内で突出して重い。

**改善案（確定）: フリーテキスト1項目**

```
ご希望の日時（任意）

┌──────────────────────────────────────┐
│ 例：来週の火・水・木の午後ならいつでも              │  ← プレースホルダー
│ 　　平日の19時以降を希望                        │
│ 　　9/25(木) の 10:00〜13:00 の間                │
└──────────────────────────────────────┘

空欄でも構いません。その場合は、こちらから候補日をいくつかご提案します。
平日夜間・土日祝のご相談にも対応しています（9:00〜21:00）。
```

**構造化UI（日付ピッカー＋時刻セレクト）を採用しない理由**

1. **このフォームは予約を確定させない。** 日程は翌営業日の返信メールで確定する運用であり、
   送信時点で構造化データを持つ必然性が薄い。
2. **構造化UIでは表現できない希望が多い。** 「来週の火・水・木の午後ならいつでも」
   「今週は難しいので再来週以降で」といった、実際に最も多い形の希望が枠で表せない。
   フリーテキストなら1行で済む。
3. **任意項目に対してコストが過大。** 枠の追加／削除、モバイルでの横幅制約、
   セレクト間の依存関係など、任意項目1つのためにフォーム内で最も複雑な実装を抱えることになる。
4. **バリデーションエラーが構造的にゼロになる。** 現行の
   「希望日時は30分以上の幅で入力してください」「開始/終了時刻を入力してください」がすべて消える。

**唯一のリスクと対処**

自由記述は「何を書けばよいか」という負荷を生む。これは本改善で最大の問題として特定した
**現行の必須「ご相談内容」欄と同じ失敗パターン**である。ただし本項目は**任意**であり空欄で素通りできること、
および**プレースホルダーに具体例を3つ置く**ことで実質的に解消する。
**プレースホルダーは飾りではなく、この項目の成否を決める要素**として扱う。

**「日程は後日メールで調整したい」チェックボックスは廃止する。**
空欄がそのまま「おまかせ」を意味するため不要になり、その意味は補助テキスト1行目が担う。

**補助テキスト（強みの明示）**

```
空欄でも構いません。その場合は、こちらから候補日をいくつかご提案します。
平日夜間・土日祝のご相談にも対応しています（9:00〜21:00）。
```

1行目が「書かなくてよい」という許可、2行目が決定事項D9の「夜間・土日祝も対応」という強みの明示。

### keywords（現行の拡張）


### AIO（AI検索）観点の設計方針

- FAQセクションは **「問い → 答え」が1ブロックで完結する形**にする。回答の1文目に結論を置く（例: Q1「初回のご相談（30分）は完全に無料です。」）。
- 「無料相談は本当に無料か」「相談だけで断れるか」「準備は必要か」は、AIアシスタントに要約されやすい典型的な問いであり、上記FAQでカバーしている。
- 「相談無料 / 30分 / オンライン / 全国対応 / 夜間・土日可 / 準備不要」という**事実の箇条書き**をHero直下に置くことで、AIが属性値として抽出しやすくなる。

### 構造化データに関する注意

`app/layout.tsx` が `faqPageJsonLd()` を**全ページに出力している**（`lib/seo/faqs.ts` の `SITE_FAQS` ベース）。
`/contact` 専用FAQを追加でJSON-LD化すると、同一ページ内に `FAQPage` が2つ存在することになり、
検索エンジンのガイドライン上リスクがある。

**推奨対応（いずれか）**

- (a) `/contact` 専用FAQはJSON-LD化せず、HTMLのみで掲載する（実装が最も簡単・推奨）
- (b) ルート layout のFAQPage出力をトップページ限定にし、各ページは自前のFAQPageを出力する（構造的に正しいが影響範囲が広い）

あわせて、`/contact` には `ContactPage`（schema.org）型の JSON-LD を追加する余地がある（FAQPageとは重複しない）。

## 7. フォーム送信API（`app/api/contact/route.ts`）への影響

### 7.1 現行APIが扱っているフィールド

```
company, name, email, content,
date1Date, date1Start, date1End,
date2Date, date2Start, date2End,
date3Date, date3Start, date3End,
date4Date, date4Start, date4End,
date5Date, date5Start, date5End
```

- 必須チェック: `if (!company || !name || !email || !content)` → 400
- 通知先: Slack Incoming Webhook（`process.env.SLACK_WEBHOOK_URL`）のみ
- Slack Block Kit の構成: ヘッダー「無料相談のご予約が届きました」／会社名・お名前・メールアドレス／ご相談内容／区切り／ご希望日時
- 希望日時は `formatSlot()` で `YYYY/MM/DD HH:MM〜HH:MM` に整形
- **申込者への自動返信メールは存在しない**

### 7.2 改修要否の判定

| 改善項目 | API改修 | 必要な改修内容 |
|---|---|---|
| Heroコピー・セクション追加・FAQ・送信完了文言 | **不要** | — |
| 「営業お断り」注記の移動 | **不要** | — |
| 会社名を任意にする | **必要** | 必須チェックから `company` を除外。未入力時のSlack表示を「（未記入）」等にフォールバック |
| 「部署・役職名」の削除 | 不要（表示文言のみ） | Slackのラベルを「会社名 / 部署・役職名」→「会社名」に変更（任意） |
| ご相談テーマをチェックボックス必須にする | **必要** | `categories: string[]` を受け取り、必須チェックの対象を `content` から `categories` に変更。Slackブロックに「ご相談のテーマ」行を追加。値はサーバ側でホワイトリスト照合すること |
| ご相談内容（自由記述）を任意にする | **必要** | 必須チェックから `content` を除外。未入力時は「（記載なし）」と表示 |
| 希望日時をフリーテキストにする | **必要（ただし削減）** | `dateNDate` / `dateNStart` / `dateNEnd` × 5枠（**15フィールド**）を `preferredDate`（string・自由記述）**1つ**に置き換える。`formatSlot()` は**関数ごと削除**。Slack通知は1ブロックで出力し、空文字のときはブロックごと省略。`preferredDate` はユーザーの自由入力がそのまま mrkdwn に渡るため、`content` / `name` と同じエスケープ方針を適用する |
| 「日程は後日メールで調整」チェック | **必要** | `scheduleLater: boolean` を追加し、true のとき希望日時ブロックに「後日メールで調整希望」と表示 |
| プライバシーポリシー同意チェック | 任意 | フロント側バリデーションのみでも成立。同意記録を残す場合は `privacy: boolean` を受け取り、false なら 400 |
| 流入元の引き継ぎ（`?from=`） | **必要** | `source: string` を受け取り、ホワイトリスト照合のうえSlackに「流入元」行を追加 |
| 申込者への自動返信メール | **必要（新規実装）** | メール送信基盤（Resend / SendGrid / Amazon SES 等）の導入が前提。送信失敗がSlack通知の成否に影響しないよう、失敗してもレスポンスは成功扱いにする等の設計判断が必要 |

### 7.3 改修時の注意点

- 現行の必須チェックはフロント・API両方に存在する。**必須項目を変更する場合は両方を同時に変更しないと、フロントで通った入力がAPIで400になる**（または逆）。
- Slack Block Kit の `section.fields` は最大10要素。テーマ・流入元を追加する場合は構成を見直すこと。
- ユーザー入力値はSlackのmrkdwnにそのまま埋め込まれている。テーマ等を選択式にする場合は、**サーバ側で許可値リストと照合**してから埋め込む方針とする。

## 10. 自動返信メールの実装方針（決定: Resend 無料枠を採用）

前提: 現状の `app/api/contact/route.ts` は Slack Webhook への通知のみで、申込者には**何も届かない**。
デプロイ先は Vercel、独自ドメインは `pit-dock.com`。`package.json` は依存最小構成（メール系ライブラリなし）。

> **決定事項D11**: 以下のA案（Resend 無料枠）を採用する。

### 10.1 選択肢の比較（採用判断の根拠）

| | A案: Resend 無料枠 **（推奨）** | B案: Google Workspace の SMTP | C案: 実装しない |
|---|---|---|---|
| 費用 | **0円**（3,000通/月・100通/日まで） | **0円**（Workspace 契約済みの場合。未契約なら不可） | 0円 |
| 送信元 | `noreply@pit-dock.com`（独自ドメイン） | 契約中のGoogleアカウントのアドレス | − |
| 必要な作業 | Resendアカウント作成／`pit-dock.com` のDNSにSPF・DKIMレコード追加／Vercelに `RESEND_API_KEY` を登録 | アプリパスワード発行／`nodemailer` 依存追加／Vercelに認証情報を登録 | 送信完了文言の調整のみ |
| npm依存 | **不要**（REST APIを `fetch` で直接呼べる） | 必要（`nodemailer`） | 不要 |
| Vercelとの相性 | ◎ HTTPS API のため Serverless Functions で安定 | △ SMTPハンドシェイクが必要でコールドスタート時に遅い。Node.js runtime 指定必須 | − |
| 上限超過時 | 送信が停止するだけで課金は発生しない | 2,000通/日（Workspace の送信上限） | − |
| 注意点 | 無料枠は1ドメイン・ログ保持30日 | 個人アカウント（@gmail.com）での業務利用は送信元の信頼性が低く非推奨 | 「送信できたか分からない」不安が残り続ける |

**想定送信数**: 無料相談の申込は多くても1日数件のため、A案の100通/日で十分に収まる。

### 10.2 実装メモ（A案・採用）

- 送信は `app/api/contact/route.ts` 内で、Slack通知の**後**に実行する。
  メール送信に失敗しても Slack 通知が成功していれば申込自体は失われないため、
  **メール送信の失敗でAPIを500にしない**（`try/catch` で握りつぶしてログのみ残す）設計とする。
- 送信元表示名は `PitDock株式会社 <noreply@pit-dock.com>`、`Reply-To` に実際の返信先アドレスを設定する。
- 自動返信の本文は §3.5 の送信完了メッセージと内容を揃える（申込内容の控え／翌営業日までに返信する旨／日程変更の連絡先）。
- **DMARCレコードの設定も併せて推奨**。SPF・DKIMのみだと Gmail 側で迷惑メール判定される可能性がある。

### 10.3 文言との連動

自動返信が実装されるまでの間は、送信完了メッセージから
「数分以内に、確認の自動返信メールをお送りします」の行を**削除した状態で**リリースする（§3.5 参照）。
Resendの実装完了後に、この行を追加する。順序を逆にすると、届かないメールを案内することになる。

### 10.4 着手時に必要な情報

- `pit-dock.com` のDNSレコードを追加できる権限（レジストラ／Vercel DNS のどちらで管理しているか）
- 自動返信メールの `Reply-To` に設定する実際の返信先アドレス
