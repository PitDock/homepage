**【残り1点・重要】子どもの利用に関する年齢要件・保護者同意の規定**

利用規約には**明確な年齢下限や未成年の保護者同意の規定がありません**（「利用者は、年齢や利用環境等、弊社の定める条件に応じて、弊社の定める範囲内で、本サービスを利用するものとします。」という抽象規定のみ）。パターンBで「お子さまの見守りに」と訴求する場合、

が必要になる可能性があります。**法務・ストア審査観点の確認をお願いします。**

→ 本書のBコピーは、この確認が取れるまで**「お子さま」を前面に出しすぎない書き方**にしています（「子どものこと、離れて暮らす親のこと」と並列で置き、子ども単独の訴求にしない）。確認が取れれば、より子ども見守りに寄せた強い表現に差し替え可能です。

> **【第3版の補足】今回確定した「保護者が代理で設定する」運用（F27）は、この年齢要件の論点と直結し、かつ有利に働きます。** 未成年の端末に保護者が自ら代理でアカウントを作成・設定するという運用が前提になるため、**保護者同意の所在が「設定を行った保護者」として整理しやすくなります**。規約に年齢要件・保護者同意条項を追加する際は、この代理設定運用を前提とした条文（例: 「未成年者が利用する場合、親権者等が代理で登録・設定を行い、本規約に同意したものとみなす」）にすることを推奨します。

## 1. 成果物1: A/B各パターンのLP構成案

### 1-0. 共通の前提（A・B不変）

- **コアメッセージ**: 「監視ではなく、つながり」。**リアルタイム追跡はしない／1日の最後に"日記"だけ共有**。
- **固有サービス名は一切出さない。** 代替として心理・状況の言語化で刺す（例: 「"今どこ"を常に見せ合うのに疲れた」「今まで使っていた位置共有アプリの代わりを探している」「見守りたいけれど監視はしたくない」）。
- **DL数・ストア評価などの数字は出さない。** 社会的証明は**プライバシー設計とデータの扱い**で代替。
- 「追跡」「監視」は**否定文脈でのみ使用**（✅「リアルタイム追跡はしません」／❌「やさしく追跡します」）。

### 1-4. 検証仮説

### 2-7. 「使い方」3ステップ 本文（A/B共通 ＋ B限定ブロック）★第3版で代理設定を書き換え

**STEP 1 — いつも通り、過ごす**
特別な操作はありません。アプリを開いたままにする必要もなく、閉じていても大丈夫です。Gentle Diary はバックグラウンドで、1日のおおまかな行動だけを静かに記録します。

**STEP 2 — 夜のあいだに、1日が「日記」になる**
毎日**深夜3時ごろ**、直近24時間の記録が自動でまとめられます。できあがるのは「9:00頃／自宅付近」「12:20頃／〇〇駅周辺」のような、時刻と場所のリスト。時刻は20分単位のおおよその表記になり、場所は「〇〇周辺」という粒度までぼかされます。同じ場所にいた間は行が増えないので、1日の節目だけが並びます。

**STEP 3 — 翌朝、やさしく届く**
できあがった日記は、承認した相手の画面に表示されます。相手が見られるのは**この日記だけ**。現在地を見る画面も、地図もありません。

**はじめにすることは、3つだけ**

1. **メールアドレスでログイン** — パスワードは不要です。届いたメールのリンクを開くだけでログインできます。
2. **位置情報の許可を「常に許可」にする** — アプリを閉じている間も1日の記録を続けるために必要です。**iOS・Android のどちらでも「常に許可」が必要**で、「アプリの使用中のみ」「1度だけ許可」を選ぶと、日記が正しく作られないことがあります。あとから端末の設定画面で変更できます。
3. **自宅の住所を登録する（任意）** — 登録しておくと、自宅から約1km以内はすべて「自宅付近」とだけ表示されます。登録した住所そのものは、誰にも公開されません。

**Q1. 相手に現在地がバレることはありますか？**

A. ありません。Gentle Diary には、相手の現在地を見る画面も、地図の上に位置を表示する機能もありません。相手に届くのは、1日1回つくられる日記だけです。日記に載るのは「時刻」と「場所」のテキストだけで、緯度・経度がそのまま共有されることはありません。時刻は20分単位のおおよその表記（「12:20頃」など）になり、場所は「〇〇駅周辺」のようにぼかされます。

---

**Q2. 相手には、具体的に何が共有されるのですか？**

A. **日記といっても、文章を書く必要はありません。1日の行動が「時刻と場所」のリストに自動でまとめられます。** 相手の画面に表示されるのは、その1日分の日記です。中身は次のようなリストです。

> 7:00頃　自宅付近
> 9:20頃　〇〇駅周辺
> 12:40頃　〇〇ビル周辺
> 19:00頃　自宅付近

時刻は20分単位に丸められ、場所は建物名または住所に「周辺」を付けた粒度になります。同じ場所にとどまっている間は行が増えないので、1日の節目だけが並びます。設定で自宅の住所を登録しておくと、自宅から約1km以内はすべて「自宅付近」とだけ表示されます（登録した住所そのものは、誰にも公開されません）。なお、相手のメールアドレスは画面上では一部を隠して表示されます。

---

**Q3. 位置情報は外部に提供されたり、ずっと保管されたりしませんか？**

A. **場所名への変換に利用する外部地図サービス以外に、位置データを第三者に提供しません。** 記録した座標を「〇〇駅周辺」のような場所の名前に変えるために外部の地図サービスを利用しており、その処理のときに座標が送信されます。それ以外の第三者への提供はありません。

また、リアルタイムの位置情報については、[利用規約](/service/products/gentle-diary/terms)に「本サービスには、リアルタイムの位置情報を第三者と共有する機能がありません」と明記しています。詳細は[プライバシーポリシー](/service/products/gentle-diary/privacy)もあわせてご確認ください。

保管についても期間を限定しています。日記をアプリ内で読めるのは**直近2日分のみ**で、3日以上前のものは閲覧できません。記録した位置情報と日記は、**取得から10日後に自動的に削除**されます。アカウントを削除すれば、データも削除されます。

**Q4. 相手とおたがいに登録しないと使えませんか？ 相手がスマホに詳しくない場合は？**

A. おたがいの登録は必須ではありません。共有は一方向ごとに独立しています。

相手の日記を見たいときは、相手のメールアドレスを入力して「閲覧申請」を送り、相手が承認すると見られるようになります。あなたの日記を相手に見せるかどうかは、これとは別の設定です。相手からあなたへの申請を、あなたが承認したときにだけ共有が始まります。つまり「自分だけが相手の日記を見る」「自分だけが相手に見せる」といった片方向の使い方もできます。承認したあとも、どちらからでもいつでも解除できますし、申請中のものはキャンセルできます。

なお、相手の日記は相手の端末で記録された位置情報から作られるため、**相手の端末にも Gentle Diary の登録と位置情報の許可が必要**です。お子さまや親御さんなど、**ご自身で設定するのが難しい場合は、あなたが代理で設定していただけます。** 相手の端末にアプリをインストールし、**相手用のメールアドレスで相手のアカウントを作り**（パスワードは不要で、届いたメールのリンクを開くだけです）、位置情報を「常に許可」にして、閲覧申請の承認までを代わりに行う流れです。

ただし、**あなた自身のアカウントで相手の端末にログインしないでください。** 位置情報も日記もあなたのアカウントのものとして記録され、相手の日記が作られません。見守りたい相手には、必ず相手自身のアカウントを作ってください（メールアドレスは、相手用に新しく用意したものでも構いません）。

2. **位置情報の許可を「常に許可」にする** — Gentle Diary は、アプリを閉じている間も1日の記録を続けることで日記を作ります。そのため **iOS・Android のどちらでも「常に許可」が必要**です。「アプリの使用中のみ」や「1度だけ許可」を選ぶと、日記が正しく作られないことがあります。あとから端末の設定画面で変更できます。

### 3-2. 週番号判定: `lib/ab/iso-week.ts`（新規）

**要件**: ISO 8601 の週番号（月曜〜日曜）。**奇数週＝A／偶数週＝B**。日本のユーザー向けなので **JST基準**（サーバはUTCのため変換必須）。

```ts
// lib/ab/iso-week.ts
export type LpVariant = "A" | "B";

/** JSTの暦日を UTC 正午基準の Date として取り出す（DST非対応地域なので固定+9hでよい） */
function toJstCalendarDate(now: Date): Date {
  const jst = new Date(now.getTime() + 9 * 60 * 60 * 1000);
  return new Date(Date.UTC(jst.getUTCFullYear(), jst.getUTCMonth(), jst.getUTCDate()));
}

/**
 * ISO 8601 の週番号と ISO週年を返す。
 * 週は月曜始まり。その週の木曜日が属する年を ISO週年とする（ISO 8601 の定義）。
 */
export function getIsoWeek(date: Date): { isoYear: number; isoWeek: number } {
  const d = toJstCalendarDate(date);
  // 月曜=1 ... 日曜=7
  const dayOfWeek = d.getUTCDay() === 0 ? 7 : d.getUTCDay();
  // その週の木曜日へ移動
  d.setUTCDate(d.getUTCDate() + 4 - dayOfWeek);
  const isoYear = d.getUTCFullYear();
  const jan1 = Date.UTC(isoYear, 0, 1);
  const isoWeek = Math.ceil(((d.getTime() - jan1) / 86_400_000 + 1) / 7);
  return { isoYear, isoWeek };
}

/** シート記録用のキー。例: "2026-W41" */
export function formatIsoWeekKey(date: Date = new Date()): string {
  const { isoYear, isoWeek } = getIsoWeek(date);
  return `${isoYear}-W${String(isoWeek).padStart(2, "0")}`;
}

/** 奇数週=A / 偶数週=B */
export function getWeeklyVariant(date: Date = new Date()): LpVariant {
  return getIsoWeek(date).isoWeek % 2 === 1 ? "A" : "B";
}
```

**検証用の既知値（実装時のユニットテストに使う）**

| 日付（JST） | 期待 isoWeek キー | 期待 variant |
|---|---|---|
| 2026-01-01（木） | `2026-W01` | A |
| 2026-01-04（日） | `2026-W01` | A |
| 2026-01-05（月） | `2026-W02` | B |
| 2026-10-08（木） | `2026-W41` | A |
| 2026-10-12（月） | `2026-W42` | B |
| 2026-12-28（月） | `2026-W53` | A |
| 2027-01-03（日） | `2026-W53` | A |
| 2027-01-04（月） | `2027-W01` | A ← **53週またぎで奇数週が連続（依頼で許容済み）** |

> 2026年はISO週が53週あるため、2026-W53（A）→ 2027-W01（A）でAが2週連続します。依頼どおり**許容**し、集計時にこのサイクルを注記します（§3-7）。

### 3-3. 出し分けの実装場所: `middleware.ts` は**不採用**

**判断理由**

1. middleware でパターンを切り替えるには、A用・B用の**別ルート（例 `/gentle-diary/a`, `/b`）への rewrite** が必要になり、そのパスが直接アクセス・クロールされうる。canonical 管理と noindex 対応が増え、SEOリスクが上がる。
2. `middleware.ts` はリポジトリに**現在存在しない**。1ページのABテストのために全リクエストを通過する仕組みを新設するのは副作用が大きい（将来の全ルートへの影響・デバッグコスト）。
3. Server Component 内で週判定して分岐レンダリングすれば、**SSR時点でパターンが確定**するため FOUC は起きず、要件（6-1 サーバ側判定・SSR描画）を満たす。
4. cookie によるランダム振り分けは不要と明示されているため、middleware の得意分野（cookie set + rewrite）を使う理由がない。

#### `lib/ab/lp-event.ts`（クライアント送信ヘルパ）

```ts
// lib/ab/lp-event.ts
"use client";

export type LpEvent = {
  isoWeek: string;
  variant: "A" | "B";
  type: "impression" | "click";
  store?: "appstore" | "googleplay";
};

const ENDPOINT = "/api/lp-event";

export function sendLpEvent(event: LpEvent): void {
  if (typeof window === "undefined") return;

  // 社内QA・E2E・クローラの混入を避ける
  if (navigator.webdriver) return;
  if (new URLSearchParams(window.location.search).has("nolog")) return;
  try {
    if (window.localStorage.getItem("lp_event_optout") === "1") return;
  } catch { /* プライベートモード等で localStorage が使えない場合は続行 */ }

  const payload = JSON.stringify({
    ...event,
    store: event.store ?? null,
    path: window.location.pathname,
    referrer: document.referrer || "",
    device: /Mobi|Android|iPhone|iPad/.test(navigator.userAgent) ? "mobile" : "desktop",
  });

  // プリフライトを避けるため text/plain で送る（APIルート側で req.text() → JSON.parse）
  const blob = new Blob([payload], { type: "text/plain;charset=UTF-8" });

  // クリック時の画面遷移でイベントが欠落しないよう sendBeacon を優先
  if (typeof navigator.sendBeacon === "function" && navigator.sendBeacon(ENDPOINT, blob)) {
    return;
  }
  // フォールバック
  void fetch(ENDPOINT, {
    method: "POST",
    body: payload,
    headers: { "Content-Type": "text/plain;charset=UTF-8" },
    keepalive: true,
  }).catch(() => { /* 計測失敗はユーザー体験に影響させない */ });
}
```

#### `_components/LpImpression.tsx`（impression を1訪問1回）

**「1訪問1回」の担保方法**

1. `sessionStorage` にキー `lp_imp:<isoWeek>:<variant>` を立て、既にあれば送らない。
   - sessionStorage はタブを閉じるまで有効なので「1訪問＝1タブセッション」の定義と一致する。
   - SPA内遷移で戻ってきても再送されない。
2. React StrictMode の effect 二重実行対策として**モジュールスコープの送信済みフラグ**も併用する（sessionStorage が使えない環境でも二重送信を防ぐ）。
3. `document.visibilityState === "visible"` のときのみ送信（バックグラウンドのプリレンダ／プリフェッチを除外）。非表示なら `visibilitychange` を1回だけ待つ。

```tsx
// app/service/products/gentle-diary/_components/LpImpression.tsx
"use client";

import { useEffect, useRef } from "react";
import { sendLpEvent } from "../../../../../lib/ab/lp-event";

let sentInThisDocument = false; // StrictMode の二重 effect / 同一ドキュメント内の再マウント対策

export default function LpImpression({
  isoWeek,
  variant,
}: { isoWeek: string; variant: "A" | "B" }) {
  const localSent = useRef(false);

  useEffect(() => {
    if (localSent.current || sentInThisDocument) return;

    const key = `lp_imp:${isoWeek}:${variant}`;
    try {
      if (window.sessionStorage.getItem(key) === "1") {
        sentInThisDocument = true;
        return;
      }
    } catch { /* sessionStorage 不可でもモジュールフラグで二重送信は防げる */ }

    const fire = () => {
      if (localSent.current || sentInThisDocument) return;
      localSent.current = true;
      sentInThisDocument = true;
      try { window.sessionStorage.setItem(key, "1"); } catch { /* noop */ }
      sendLpEvent({ isoWeek, variant, type: "impression" });
    };

    if (document.visibilityState === "visible") {
      fire();
      return;
    }
    const onVisible = () => {
      if (document.visibilityState === "visible") {
        document.removeEventListener("visibilitychange", onVisible);
        fire();
      }
    };
    document.addEventListener("visibilitychange", onVisible);
    return () => document.removeEventListener("visibilitychange", onVisible);
  }, [isoWeek, variant]);

  return null;
}
```

#### `app/api/lp-event/route.ts`

既存 `app/api/contact/route.ts` の作法（環境変数チェック → 許可値照合 → 外部エンドポイントへ `fetch` → JSON返却）に揃えています。

```ts
// app/api/lp-event/route.ts
import { NextRequest, NextResponse } from "next/server";

export const runtime = "nodejs";
export const dynamic = "force-dynamic";

const ALLOWED_VARIANTS = ["A", "B"] as const;
const ALLOWED_TYPES = ["impression", "click"] as const;
const ALLOWED_STORES = ["appstore", "googleplay"] as const;

export async function POST(req: NextRequest) {
  const endpoint = process.env.LP_EVENT_ENDPOINT_URL;
  const token = process.env.LP_EVENT_TOKEN;
  if (!endpoint || !token) {
    // 計測設定が無くてもユーザー体験を壊さないため 204 を返す
    console.warn("[lp-event] LP_EVENT_ENDPOINT_URL / LP_EVENT_TOKEN not configured");
    return new NextResponse(null, { status: 204 });
  }

  // sendBeacon は text/plain で送るため text() で読む
  let body: Record<string, unknown>;
  try {
    body = JSON.parse(await req.text());
  } catch {
    return NextResponse.json({ error: "Invalid JSON" }, { status: 400 });
  }

  // 受け取った値はそのまま外部に流さず、許可値と照合する（contact/route.ts と同じ方針）
  const variant = String(body.variant ?? "");
  const type = String(body.type ?? "");
  const rawStore = body.store == null ? "" : String(body.store);

  if (!(ALLOWED_VARIANTS as readonly string[]).includes(variant)) {
    return NextResponse.json({ error: "Invalid variant" }, { status: 400 });
  }
  if (!(ALLOWED_TYPES as readonly string[]).includes(type)) {
    return NextResponse.json({ error: "Invalid type" }, { status: 400 });
  }
  const store =
    type === "click" && (ALLOWED_STORES as readonly string[]).includes(rawStore) ? rawStore : "";
  if (type === "click" && !store) {
    return NextResponse.json({ error: "Invalid store" }, { status: 400 });
  }

  // ISO週キーは "YYYY-Www" のみ許可（任意文字列をシートに書かせない）
  const isoWeek = String(body.isoWeek ?? "");
  if (!/^\d{4}-W\d{2}$/.test(isoWeek)) {
    return NextResponse.json({ error: "Invalid isoWeek" }, { status: 400 });
  }

  const path = String(body.path ?? "").slice(0, 200);
  const referrer = String(body.referrer ?? "").slice(0, 300);
  const device = body.device === "mobile" ? "mobile" : "desktop";

  try {
    const res = await fetch(endpoint, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      // Apps Script の /exec は 302 で googleusercontent に飛ぶため follow が必要
      redirect: "follow",
      body: JSON.stringify({
        token,
        event: { isoWeek, variant, type, store: store || "―", path, referrer, device },
      }),
    });
    if (!res.ok) {
      console.error("[lp-event] GAS responded", res.status);
    }
  } catch (e) {
    // 計測の失敗はユーザーに影響させない
    console.error("[lp-event] forward failed:", e);
  }

  return new NextResponse(null, { status: 204 });
}
```

### 3-5. Google Apps Script（スプレッドシート書き出し）

**セットアップ手順**

1. Google スプレッドシートを新規作成（名称例: `Gentle Diary LP ABテスト`）。
2. シートを2枚用意し、名前を **`raw`** と **`集計`** にする。
3. `raw` の1行目に見出しを入れる（§3-6 の列定義）。
4. 拡張機能 → **Apps Script** を開き、下記コードを貼る。
5. `SHEET_ID` を当該スプレッドシートのID（URLの `/d/` と `/edit` の間）に置き換える。
6. `TOKEN` に十分に長いランダム文字列を設定（例: `openssl rand -hex 24` の出力）。**これを `LP_EVENT_TOKEN` にも同じ値で設定する。**
7. **デプロイ → 新しいデプロイ → 種類「ウェブアプリ」**
   - 「次のユーザーとして実行」= **自分**
   - 「アクセスできるユーザー」= **全員**（トークンで認証するため）
8. 発行された **`https://script.google.com/macros/s/.../exec`** を `LP_EVENT_ENDPOINT_URL` に設定。
9. コードを修正したら**必ず「デプロイを管理」→ 新バージョンで再デプロイ**する（保存だけでは `/exec` に反映されない）。

```javascript
// Google Apps Script（コード.gs）
const SHEET_ID = 'ここにスプレッドシートIDを入れる';
const SHEET_NAME = 'raw';
const TOKEN = 'ここに LP_EVENT_TOKEN と同じ値を入れる';

const ALLOWED_VARIANTS = ['A', 'B'];
const ALLOWED_TYPES = ['impression', 'click'];
const ALLOWED_STORES = ['appstore', 'googleplay', '―'];

function doPost(e) {
  try {
    if (!e || !e.postData || !e.postData.contents) {
      return json_({ ok: false, error: 'no body' });
    }
    const body = JSON.parse(e.postData.contents);

    if (body.token !== TOKEN) {
      return json_({ ok: false, error: 'unauthorized' });
    }

    // 単発 event / 配列 events の両方を受ける
    const events = Array.isArray(body.events) ? body.events : [body.event];

    const sheet = SpreadsheetApp.openById(SHEET_ID).getSheetByName(SHEET_NAME);
    if (!sheet) return json_({ ok: false, error: 'sheet not found' });

    const rows = [];
    for (let i = 0; i < events.length; i++) {
      const ev = events[i] || {};
      if (!/^\d{4}-W\d{2}$/.test(String(ev.isoWeek))) continue;
      if (ALLOWED_VARIANTS.indexOf(String(ev.variant)) === -1) continue;
      if (ALLOWED_TYPES.indexOf(String(ev.type)) === -1) continue;
      const store = ALLOWED_STORES.indexOf(String(ev.store)) === -1 ? '―' : String(ev.store);
      rows.push([
        new Date(),                      // A タイムスタンプ
        String(ev.isoWeek),              // B ISO年-週番号
        String(ev.variant),               // C パターン
        String(ev.type),                  // D 種別
        store,                            // E ストア
        String(ev.path || ''),            // F パス
        String(ev.referrer || ''),        // G リファラ
        String(ev.device || ''),          // H デバイス
      ]);
    }
    if (rows.length === 0) return json_({ ok: false, error: 'no valid events' });

    // 同時書き込みで行が壊れないよう排他する
    const lock = LockService.getScriptLock();
    lock.waitLock(20000);
    try {
      sheet.getRange(sheet.getLastRow() + 1, 1, rows.length, rows[0].length).setValues(rows);
    } finally {
      lock.releaseLock();
    }
    return json_({ ok: true, count: rows.length });
  } catch (err) {
    return json_({ ok: false, error: String(err) });
  }
}

function doGet() {
  // 疎通確認用
  return json_({ ok: true, service: 'gentle-diary-lp-event' });
}

function json_(obj) {
  return ContentService.createTextOutput(JSON.stringify(obj))
    .setMimeType(ContentService.MimeType.JSON);
}
```

### 3-6. シート列定義

#### `raw` シート（1行目は見出し固定）

| 列 | 見出し | 内容 | 例 |
|---|---|---|---|
| A | タイムスタンプ | GAS が記録した日時 | `2026/10/08 14:32:11` |
| B | ISO年-週番号 | `YYYY-Www` | `2026-W41` |
| C | パターン | `A` / `B` | `A` |
| D | 種別 | `impression` / `click` | `click` |
| E | ストア | `appstore` / `googleplay` / `―` | `appstore` |
| F | パス | 表示されていたパス | `/service/products/gentle-diary` |
| G | リファラ | `document.referrer` | `https://www.google.com/` |
| H | デバイス | `mobile` / `desktop` | `mobile` |

> F〜H は依頼の必須列ではありませんが、**流入経路の偏り（§3-8 の最大の交絡要因）を後から診断するために必須級に重要**です。特に **G列（リファラ）は §3-8 の解釈指針で必ず確認する項目**です。

#### `集計` シート

1行目を見出しにし、2行目に以下を入れて下方向にコピーします。

| 列 | 見出し | 数式（2行目） |
|---|---|---|
| A | ISO年-週番号 | `=SORT(UNIQUE(FILTER(raw!B2:B, raw!B2:B<>"")))` ※A2に1つだけ入れると縦に展開 |
| B | パターン | `=IFERROR(INDEX(FILTER(raw!$C$2:$C, raw!$B$2:$B=$A2), 1), "")` |
| C | 表示数 | `=COUNTIFS(raw!$B$2:$B, $A2, raw!$D$2:$D, "impression")` |
| D | クリック数 | `=COUNTIFS(raw!$B$2:$B, $A2, raw!$D$2:$D, "click")` |
| E | **クリック率** | `=IFERROR(D2/C2, "")` ※セル書式をパーセントに |
| F | App Store | `=COUNTIFS(raw!$B$2:$B, $A2, raw!$D$2:$D, "click", raw!$E$2:$E, "appstore")` |
| G | Google Play | `=COUNTIFS(raw!$B$2:$B, $A2, raw!$D$2:$D, "click", raw!$E$2:$E, "googleplay")` |
| H | mobile表示数 | `=COUNTIFS(raw!$B$2:$B, $A2, raw!$D$2:$D, "impression", raw!$H$2:$H, "mobile")` |

**パターン別の累計（判定に使う本体）** — 同じ `集計` シートの右側（例 K〜O列）

| セル | 内容 | 数式 |
|---|---|---|
| K1 | 見出し | `パターン` / `表示数` / `クリック数` / `クリック率` / `対象週数` |
| K2 | A | `A` |
| L2 | A 表示数 | `=SUMIF($B$2:$B, "A", $C$2:$C)` |
| M2 | A クリック数 | `=SUMIF($B$2:$B, "A", $D$2:$D)` |
| N2 | **A クリック率** | `=IFERROR(M2/L2, "")` |
| O2 | A 対象週数 | `=COUNTIF($B$2:$B, "A")` |
| K3 | B | `B` |
| L3 | B 表示数 | `=SUMIF($B$2:$B, "B", $C$2:$C)` |
| M3 | B クリック数 | `=SUMIF($B$2:$B, "B", $D$2:$D)` |
| N3 | **B クリック率** | `=IFERROR(M3/L3, "")` |
| O3 | B 対象週数 | `=COUNTIF($B$2:$B, "B")` |
| N5 | 差（B − A） | `=IFERROR(N3-N2, "")` |
| N6 | 相対差 | `=IFERROR(N3/N2-1, "")` |

### 3-7. 判定ルール

1. **判定指標はクリック率（クリック数 ÷ 表示数）**。週ごとに流入量が違うため、**クリック"数"の単純比較はしない**。
2. **複数サイクルを積み上げてから結論を出す。最低3サイクル（Aが3週・Bが3週＝合計6週）。**
   週替わりは時系列比較なので、季節性・キャンペーン・SNS投稿・ストア掲載順位の変動といった**週固有の要因がパターンと分離できません**。1サイクル（A1週＋B1週）で出た差は、セグメントのフレーミングの差ではなく「その週に何があったか」の差である可能性が十分にあります。
3. **サンプルサイズの目安**: ベースのクリック率が5〜10%の場合、**2ポイントの差を有意に検出するには、おおよそ 2,000〜3,500 impression／パターン**が必要です（有意水準5%・検出力80%の概算）。
   - `集計` シートの `L2` / `L3`（パターン別表示数）がこの水準に届いていない場合、差が出ても**方向性の参考値**として扱い、意思決定の根拠にしないこと。
   - 週あたり数十〜百 impression 規模が続く場合は、6週では到達しません。その場合は**サイクル数をさらに積む**か、将来的に週替わりから**週内同時分割（cookie振り分け）へ設計変更**する判断が必要です（本件は週替わり指定のため Phase 2 の検討事項）。
4. **53週またぎのサイクル**（例 2026-W53 → 2027-W01 で A が2週連続）は、集計時に注記する。Aの表示数が一時的に多くなるため、判定はクリック率で行う原則がここでも効く。
5. **判定の正データはスプレッドシート**。Slack通知は実装しない。
6. **社内トラフィックの除外**: QAや関係者の閲覧は `?nolog=1` を付けてアクセスする、または一度 `localStorage.setItem("lp_event_optout","1")` を実行する（§3-4 の送信ヘルパで対応済み）。この運用ルールを関係者に周知すること。
7. **【★2026-10-09 追加】常時表示CTA（下部固定バー／ヘッダー内バッジ）のクリックも計測対象**です。`StoreCta` を通るため、本文4箇所のクリックと同じ `click` イベントとして `raw` に入ります。
   - **A/B とも完全に同一仕様**（共通コンポーネントから出力）なので、**A と B のクリック率比較は引き続き有効**です。
   - ただし常時表示CTAの追加で**クリック率のベースライン自体が上がります**。この変更より前に溜まったデータがある場合は、**同じ集計に混ぜないでください**（比較するなら、変更日以降のデータだけで3サイクル積み直す）。
   - どのCTAが効いたかを切り分けたい場合は、`raw` に CTA 位置の列を足す改修が必要です（現仕様では位置を記録していません）。本テストの独立変数はターゲットのフレーミングなので、Phase 1 では位置の切り分けは行いません。

### 3-8. この設計が測れるもの／測れないもの（セグメントA/Bであることによる重要な解釈指針）

> **独立変数が「ターゲットセグメント」であるため、結果の解釈には次の制約が加わります。判定の前に必ず読んでください。**

**A/B とも同じ流入に対して表示されるため、このテストが測るのは「既存の流入をどちらのフレーミングがより転換させるか」であり、「どちらのセグメントの市場が大きいか」ではありません。**

流入が検索・広告経由でカップル寄り（または見守り寄り）に偏っている場合、**不利な側のパターンが構造的にハンデを負います**。たとえば流入の8割が「カップル 位置共有」系のクエリから来ていれば、B（家族見守り）は内容の優劣とは無関係に負けます。これは「見守り市場が小さい」ことの証明にはなりません。

**したがって判定時に必ず行うこと**

1. `raw` の **G列（リファラ）で、A週とB週の流入構成を必ず確認する**（§3-6 の流入確認クエリを使用）。
2. 流入キーワード／経路が偏っている場合、結果は**「セグメントの優劣」ではなく「現在の流入との相性」として解釈する**。レポートにもその旨を明記する。
3. Search Console の検索クエリも併せて確認し、このURLに実際に来ている検索意図がカップル寄りか見守り寄りかを把握する。
4. **セグメント自体の規模を測りたい場合は、流入側（広告クリエイティブ・検索キーワード・LP自体の分離）を分けた別テストが必要**です。本テストでは測れません。
5. A週とB週でリファラ構成が大きく違っていた週があれば、その週を**注記付きで扱う**（除外するかは除外後のサンプル数を見て判断。恣意的な除外を避けるため、除外する場合は理由と除外前後の両方の数字を残す）。

**勝敗ごとの解釈指針は §1-4 の表を参照してください。**

### 3-10. SEO・構造化データ（A/B共通・交絡防止）

- **title / description / keywords / canonical は `layout.tsx` に1つだけ**置く（§2-10）。**A/Bで変えない。**
- canonical は `/service/products/gentle-diary` の1本。rewrite しないため別URLは生まれない。
- JSON-LD は duosub の作法に揃え、`JsonLd` コンポーネントで以下3つを出力（**A/B同一**）:
  - `webPageJsonLd({ name: PAGE_TITLE, description: PAGE_DESCRIPTION, path: PAGE_PATH })`
  - `softwareApplicationJsonLd({ name: "Gentle Diary", description: PAGE_DESCRIPTION, path: PAGE_PATH, operatingSystem: "iOS, Android", applicationCategory: "LifestyleApplication", downloadUrl: [APP_STORE_URL, GOOGLE_PLAY_URL], image: "/images/products/GentleDiary.png", offers: { price: "0", priceCurrency: "JPY", description: "無料" } })`
  - `faqPageJsonLd(GENTLE_DIARY_FAQS)`

**セグメントがA/Bで変わることに伴うSEO前提**

セグメントがA/Bで変わるため、**キーワードがどちらか一方のパターンにしか存在しない状態を作ってはいけません**（Googlebot がどちらのHTMLをクロールするか制御できないため、キーワードの偏りがそのままSEO差＝交絡要因になります）。したがって:

1. **指定5キーワードは、A・B両方のHTMLに必ず存在させる。**
   - 「カップル 位置共有」「家族 見守り」は **§2-11 のH2群に両方含まれており、そのH2はA・B両方に置く**。
   - Aにしかない「A6 誰のため」の H2「カップル・夫婦の位置共有に、家族の見守りに」が**Aのみに存在すると偏りが生じる**。これを避けるため、**B にも同じ文言のH2を持つセクションを置く**: Bでは `B6 社会的証明` の直前に**「カップル・夫婦の位置共有に、家族の見守りに」を見出しに持つコンパクトな帯（3行程度）**を入れること。中身のリード文はBの文脈（見守り主軸）で書くが、**H2文言はAと一字一句同じ**にする。
   - 同様に、Bにしかない「B4 粒度」の H2「届くのは、1日分の位置情報日記だけ」が**Bのみに存在すると偏りが生じる**。**Aでは A3 解決提示のセクション内に同じ趣旨の見出しを含める**か（推奨）、A3 の直後に同じH2の小ブロックを置くこと（§2-11 末尾の注記）。
2. **alt のキーワードも A・B 両方に存在させる。** §2-12 のうち、A・B両方で使う画像（S1 / S2 / S5 / S7 / D1 / D2 / D3 / D4 / D5）にキーワードを配置しているので、この配置を崩さないこと。BのみのD8・D9にはキーワードを入れていない（偏り防止）。
3. **FAQ本文は A/B 完全同一**（§2-9）。これが最大の長文キーワード供給源なので、ここを揃えておけばSEO差はほぼ生じません。
4. `_components/VariantA.tsx` / `VariantB.tsx` は `"use client"` ですが、Next.js はクライアントコンポーネントも**SSRでHTMLを出力**します。CTA・FAQ・H2のテキストはHTMLに含まれるので、SEO・AIO上の問題はありません。

> **builder への検証手順**: 実装後、A・B両方のHTMLを取得して、指定5キーワードそれぞれの出現箇所数が**A・Bでほぼ同数**であることを確認してください。
> 例: `getWeeklyVariant` をA固定／B固定にそれぞれモックして、`curl -s "http://localhost:3000/service/products/gentle-diary" | grep -o "家族 見守り" | wc -l` を2回実行し、数を比較。「位置情報 日記」「カップル 位置共有」「監視しない 位置共有」「位置情報共有 アプリ」も同様に。
